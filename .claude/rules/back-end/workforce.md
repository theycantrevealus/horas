# Back End Workforce (HR)

The workforce context (`apps/back-end/apps/workforce`, alias `@workforce/*`) holds the domain rules of the Human Resource Management module. It is exposed over HTTP by `gateway_hr` (`apps/back-end/apps/gateway_hr`). Business source: `.claude/business/administrative-operational-system/human-resource-management.md`. Collections: `.claude/design/human-resource-collections.md` and `account-and-workforce-collections.md`. Endpoints and build order: `.claude/design/hr-endpoints.md` and `.claude/design/plans/`. Repository rules: `database.md`. Logging rules: `logging.md`. Placement: `placement.md`.

Rules:

- The context stays transport-neutral: no HTTP, headers or Nest request types in `apps/workforce` (`placement.md`).
- `apps/workforce` may import `apps/repository`, `apps/utility`, `apps/configuration` and, for tests only, `apps/identity/testing`. It must not import identity services. `gateway_hr` imports identity only for its guards, decorators, filter, permission catalog and `AuthenticatedUser`.
- Do not duplicate `identity`'s error classes. Use the workforce ones.

## 2. Sign-in

`gateway_hr` shares sign-in with `gateway_back_office`: the same `AuthenticationGuard` and `PermissionsGuard`, the same `AUTH_JWT_SECRET`, the same database. It has no login or refresh route; users sign in on `gateway_back_office` and use the access token on both gateways (`authentication.md` 3). Both must therefore run with the same `auth.env`.

## 3. Rules for every HR endpoint

- **Tenant.** Services receive `tenant_id` from `@CurrentUser()`. A record of another tenant, a missing record and a malformed id all answer 404 with the same code. Never take the tenant or `employee_id` from a request body or query.
- **Reads write no log entry**, on success or on failure (`logging.md` 4.3). Do not wrap a read in `observe`. Name repository reads `find*`.
- **Writes** go through `observe` with an event name `<noun>_<verb>` (for example `organization_create`) and write one entry with the shared fields. Never log request values, names, identifiers or numbers; log the error class and the workforce `code`.
- **Change history.** Every write is recorded by the repository (`database.md` 6.1). An optional `reason` in the request body is passed with `withChangeReason`. Do not add `updated_by` or history fields.
- **Concurrency.** Update bodies accept an optional `version`. A stale version answers 409 `stale_version`.
- **Parents.** A record that points to a parent (a facility to its organization) checks that the parent exists in the tenant, is active and is not soft-deleted. A missing, deleted and foreign parent give one answer (422 `<parent>_not_found`), so nothing leaks across tenants. Deactivating a parent is refused (409 `<parent>_in_use`) while it has active children.
- **Immutable fields.** A field that other records depend on (a code, a country, a time zone, a parent) is not in the repository's `updatableFields`, not in the update DTO, and not in the update service input. A request that sends only immutable fields answers 422 `empty_update`.
- **No delete.** HR records are set inactive or closed, never deleted, unless the collection design says otherwise.
- **Validation.** The DTO checks shape and length (400). The service checks business rules (422), so a second transport would get the same rules. A code from a code system (a `Coding`) is validated with `CodeConceptService.assertActive(tenantId, coding)`: the concept must exist (the tenant's own or platform-wide), be active and cover today. Never accept a `Coding` unchecked, and never copy a code list into the service.
- **Paging.** Lists accept `limit` (1 to 100) and `offset` (0 or more) and reject other values; without `limit` the repository default applies (`DEFAULT_PAGE_SIZE`, 10). Lists are ordered by a stable field, usually `code`.
- **Responses** are models: no `_id`, no `__v`.

## 3a. Assignments

- An employee has at most one open primary assignment and a head-of-unit position at most one open holder (partial unique indexes on `is_open`). Other checks (409 `fte_exceeded`, `headcount_exceeded`) read then write, so two simultaneous creates can both pass.
- Overlapping open assignments under one contract must not exceed the contract's `fte`. Acting assignments do not count against a position's budgeted headcount.
- An assignment lies inside its contract's period; acting and secondment need an end date. It is created `planned` when it starts after today in the facility's zone, otherwise `active`. Nothing activates a planned assignment yet.
- Assignments are never edited or deleted: end one (`POST /assignments/:id/end`) and create another. A position with an open assignment cannot be closed (409 `position_in_use`).

## 3b. Committee memberships

- A person has at most one active membership in a committee of a facility (409 `membership_exists`); a committee of a facility has at most one active chair and one active secretary (409 `chair_exists`, `secretary_exists`). Partial unique indexes on `status: 'active'` back the checks.
- The committee and the role are codes (`id.committee`, `id.committee-role`), checked with `assertActive`. The member must be an employee of the tenant who has not separated; the facility must be active.
- An appointment starts no later than tomorrow in the facility's zone and its end, if given, is not in the past; a membership ends on a date from its start to tomorrow. Nothing is edited or deleted: end a membership and appoint again.

## 3c. Licences

- A licence starts `pending_verification`. Only a different account than the submitter may verify it (403 `verifier_is_submitter`), and only HR Admin holds `workforce.license:verify`.
- The licence type (a code concept) decides what a licence needs: `requires_expiry_date` (expiry date), `location_specific` (a practice location) and `eligibility_role` (copied onto the licence). A document number is unique per type while the record is live (normalized: upper case, no spaces, dots or hyphens). The scan is a file reference only (`file_id`, content type, SHA-256); nothing checks that the file exists.
- A match needs the licence's profession to equal the employee's and its specialty to be empty or equal the employee's primary specialty. An expired licence, or one issued later than today (UTC), cannot be verified. A mismatch rejects it with a reason; nothing is edited or deleted, a corrected licence is registered anew.
- At most one valid practice permit per employee, profession and facility (409 `valid_license_exists`). A renewal names the valid licence it replaces; verifying it supersedes that one.
- Nothing expires licences yet: a `valid` licence past its date stays `valid` until a worker job exists, so eligibility must read the date too.

## 3d. Professional credits

- A credit record (SKP, CME, CPD) is `accepted` when HR records it and `submitted` when the employee submits it, which needs evidence. A submitted record is accepted or rejected, an accepted one may later be rejected, a rejected one is final. The reviewer is never the holder (403 `reviewer_is_holder`) and a rejection carries a reason in the change history; the model has no review fields. Nothing is edited or deleted.
- The credit system and the activity category are codes (`id.credit-system`, `id.cpd-category`), checked with `assertActive`. Points are above 0, at most 500, with at most two decimals; the activity date runs from 1950 to tomorrow (UTC). Evidence is a file reference only.
- A credit total is one per employee and credit system, read from a national platform: a new `PUT` replaces the old total and the old values stay in the change history. The path's credit system code must equal the body's. The list adds `accepted_points`, the accepted records of that system inside the total's cycle, computed on read.
- The limits of 500 points per record and 10000 per total are guesses, not regulation. Credits do not affect licences, and the SIP-renewal shortfall alert (`HR-LIC-010`) is not built.

## 3e. Privilege catalog

- A catalog item has an upper-case code, unique per tenant and fixed (409 `privilege_exists`), and an owning committee that is fixed too. At least one profession may request it; specialties are optional (empty means any), as are the career level, the required evidence (at most one per evidence type), the external procedure codes and the facilities (empty means every facility of the tenant).
- Every profession, specialty, level, committee and evidence type is a code checked with `assertActive`; external procedure codes are checked for format only; each facility must exist in the tenant and not be deleted.
- Retiring is final: a retired item cannot be edited or reactivated (422 `privilege_retired`), and a privilege that is needed again is added with a new code. Existing grants keep pointing to a retired item. Nothing is deleted.
- Read and write are tenant-wide permissions: any holder of `workforce.privilege:write` can edit any committee's items until scoped permissions exist.

## 3f. Credential applications

- An application is a request of a clinical employee for privileges, started by HR (`workforce.credential-application:write`; the applicant has no routes yet). Types `initial`, `temporary`, `recredentialing` and `privilege_extension` (the last two are renewals, 3h); the committee comes from the employee's workforce category and the scope from `CREDENTIALING_SCOPE`, both copied when the application is created. The applicant, facility, committee, scope and type never change.
- Status flow: `draft` to `submitted`, `under_review`, `assessed`, `recommended`; `returned` goes back to `draft` when edited; `withdrawn` is possible until the application is assessed. Any other move answers 422 `invalid_transition`. `approved` and `rejected` come from the Director's decision (3g). Every change sets `status_since`; return and withdraw need a reason of 1 to 500 characters. Nothing is deleted.
- **Committee routes** (start review, return, appoint assessors, read assessments) need `workforce.credential:review` and an active seat, in any role, in the applicant's committee at the credentialing facility (403 `not_committee_member`). The recommendation needs the chair (403 `not_committee_chair`). A missing, foreign or malformed application answers 404 before any seat check. Committee membership stands in for scoped permissions.
- **Assessors** are employees of the tenant who have not separated, are not the applicant and hold an active `mitra_bestari` seat in that committee (422 `assessor_not_eligible`). Appointing needs `under_review`, takes 1 to 20 employees, is all or none and additive. A temporary application is not assessed (422 `assessment_not_required`).
- **The assessor's routes are personal:** no permission, the caller's employee must be one of the application's assessors (403 `not_an_assessor`). A conflict declaration is made once, while `under_review`, and is final; a conflict needs a code of `id.conflict-relationship`. An assessment needs a declaration first, is refused after a conflict (403 `conflict_declared`), covers every requested privilege once, and is made once per assessor (409 `assessment_exists`). The findings and the move to `assessed` (every assessor without a conflict has assessed, at least `MIN_ASSESSORS` of them) share one transaction.
- **Assessments are highly confidential.** Reading them records one access entry per assessment returned in the change log (`recordAccess`, after the read); if recording fails nothing is returned. A `mitra_bestari` seat sees only its own findings. Reads write no operational log entry.
- **Redaction.** A caller without a seat in the applicant's committee gets applications without the assessors' conflict declarations and the recommendation summary (`GET :id`, the queue and the responses of update, submit and withdraw).
- **Recommendation.** A decision for every requested privilege, never more permissive than requested (`full` above `supervised` and `restricted`; those two may swap); `supervised` needs a supervisor who is another employee of the tenant, `restricted` needs notes; a summary of 1 to 2000 characters. Everything not recommended is still a recommendation; the Director rejects it in 4.3.
- No events and no notifications; service-level alerts (`CREDENTIAL_SLA_DAYS`) wait for the worker; the check that a supervisor's own grant is `full` is made when the SPK is issued (3g). `MIN_ASSESSORS` is read at facility level, so its default applies until committee-scope parameters exist.

## 3g. SPKs and granted privileges

- **The Director's decision** (`POST /v1/credential-applications/:id/decision`, `workforce.credential:decide`) acts only on a `recommended` application. The caller's own employee is recorded as the Director, so an account without a linked employee answers 403 `director_employee_required`, and the applicant cannot decide their own application (403 `decider_is_applicant`). Who the Director is, or a delegate, is whoever the administrator gave the permission to; no position or role says it. A missing, foreign or malformed application answers 404 first.
- **Rejecting** needs a reason of 1 to 500 characters, sets the application to `rejected` and writes no SPK.
- **Approving** writes, in one transaction, the SPK (`active`, current) and one grant per privilege the committee recommended, and sets the application to `approved`. A grant takes its condition, supervisor and restriction notes from the recommendation, never from the request, and starts `active`. It needs a letter number (`appointmentNumber`: upper case letters, digits, `/`, `.`, `-`, 1 to 64 characters, unique per tenant, 409 `appointment_number_exists`). It answers 422 `nothing_recommended` when nothing was recommended, `privilege_not_found` or `privilege_retired` for a catalog item that is gone or retired since the request, `employee_separated` and `facility_not_found`.
- **Licences (`HR-CRD-002`).** On the issue date the applicant needs a valid registration and, for every facility of the SPK, a valid practice permit (422 `license_not_valid`). Valid means status `valid`, issued on or before the date and not expired on it: nothing expires licences yet, so the dates are read too.
- **Validity (`HR-CRD-004`).** The SPK starts on the issue date, today in the credentialing facility's zone, and ends at most `SPK_VALIDITY_YEARS` years later minus one day; a temporary SPK ends at most the requested days later counting the first day. `validUntil` may be earlier, never later or before the start (422 `invalid_validity`). The signed letter is a file reference only (422 `invalid_document`).
- **One current SPK.** A person has at most one current (`active` or `suspended`) non-temporary SPK per credentialing facility (409 `appointment_exists`); temporary SPKs are not limited by that index. A renewal does not meet that check: it supersedes the current SPK (3h).
- **Supervised grants (`HR-CRD-006`).** The supervisor named in the recommendation must hold an active `full` grant of the same privilege in an active SPK of the credentialing facility; the grant stores `supervisor` with that grant's identifier (422 `supervisor_not_privileged`).
- **Reads** are tenant-wide with their own permissions and write no log entry. `GET /v1/clinical-appointments` lists by `status`, `employeeId`, `facilityId` and `unitId` (covered places), ordered by the end of validity; `expiringInDays` keeps current SPKs ending within that many days from today (UTC), lapsed ones included, because nothing sets `expired` yet, so every consumer reads `valid_period.end` too. `GET /v1/clinical-appointments/:id` returns `{ appointment, grants }` with every grant whatever its status. `GET /v1/employees/:id/clinical-appointments` answers 404 `employee_not_found` for an employee of another tenant. `GET /v1/privilege-grants` shows active grants by default (`status=all` for every status) and filters by privilege, practitioner, condition, place and `flagged` (an open flag).
- **The Director's later decisions** (`workforce.credential:decide`) take `reason` (1 to 500 characters), `decisionNumber` (1 to 64 characters) and an optional `version`. The effective date is not sent: it is today in the credentialing facility's zone. `suspend` takes an `active` SPK to `suspended`; `lift-suspension` takes a `suspended` one back to `active`, clears `suspension` and needs a new decision, which the change history records; `revoke` takes `active` or `suspended` to `revoked`, sets `is_current` to false and revokes every grant of the SPK that is not revoked with the same decision. Suspending an SPK leaves its grants alone: eligibility reads the SPK status (`HR-CRD-001`). `revoked`, `expired` and `superseded` are final (422 `invalid_transition`).
- **A single grant** is suspended (`active` to `suspended`), has its suspension lifted, or is revoked (final) the same way. A grant of an SPK that is not current answers 422 `appointment_not_current`, checked before the transition.
- **Supervisor flags.** When a `full` grant stops being active (suspended or revoked directly, or through the suspension or revocation of its SPK), the `supervised` grants that name it get the open flag `supervisor_lost_privilege` in the same transaction; a revoked, superseded or already flagged grant is left alone. Lifting the suspension of the grant or the SPK resolves the flags (`resolved_at`); lifting a grant inside a suspended SPK leaves them open until the SPK is lifted. There is no route to resolve a flag by hand and no alert is sent.
- Decisions are logged as `appointment_suspend`, `appointment_lift_suspension`, `appointment_revoke`, `grant_suspend`, `grant_lift_suspension`, `grant_revoke` and `application_decide`, with a count of flags set or resolved and never a reason, number or letter. No events are emitted. The in-memory repositories cannot roll back, so tests check results, not a failure inside a transaction.

## 3h. Renewals (re-credentialing and privilege extension)

- **Starting a renewal** is `POST /v1/credential-applications` with type `recredentialing` or `privilege_extension` and `previousAppointmentId`, the SPK being renewed. The SPK is required for a renewal (422 `previous_appointment_required`) and refused for `initial` and `temporary` (422 `previous_appointment_not_allowed`). It must be the applicant's own regular SPK at the credentialing facility and `active`: 422 `previous_appointment_not_found` (missing, malformed or another tenant's), `previous_appointment_mismatch`, `previous_appointment_not_regular`, `previous_appointment_not_active`. A suspended SPK is renewed only after the Director lifts the suspension, and a temporary SPK is never renewed. At most one renewal is open per SPK (409 `renewal_exists`; open means not `approved`, `rejected` or `withdrawn`).
- **Content.** A privilege extension asks only for additional privileges: one the SPK holds as an `active` or `suspended` grant answers 422 `privilege_already_granted`. A re-credentialing asks for everything the practitioner should keep and may repeat held privileges; a privilege not re-requested, or not recommended, ends with the old SPK. The type and the SPK are fixed after creation; an edit rechecks the SPK, the open renewal (not against itself) and the held privileges. Assessment, the committee and the recommendation work as for an initial application.
- **Approving a renewal** (the same decision route, 3g) needs the old SPK still `active`, the applicant's own and at the facility (422 `previous_appointment_not_found`, `previous_appointment_mismatch`, `previous_appointment_not_active`), and in one transaction: the old SPK stops being current, the new SPK is issued, its grants are created, the old SPK becomes `superseded` (`superseded_by_id`) and its `active` and `suspended` grants become `superseded`, then the application is approved. A stale old SPK answers 409 `previous_appointment_changed`; a second approval for the same SPK fails because it is no longer active.
- **Re-credentialing** is valid from the issue date for at most `SPK_VALIDITY_YEARS` years, may be approved after the old SPK ended, covers the requested units and has one grant per recommended privilege. **A privilege extension** keeps the old last valid day and refuses `validUntil` (422 `valid_until_not_allowed`), is refused when that day has passed (422 `appointment_lapsed`), covers the union of the old and the requested units and facilities (the licences are checked for all of them), and carries the old `active` and `suspended` grants over as new records with their condition, supervisor, notes, status, decision and flag, plus one grant per recommended additional privilege. A Director's suspension is not lifted by a renewal; revoked grants stay with the old SPK.
- **`superseded`** is a final status of an SPK and of a grant. The privilege directory lists active grants by default, so a privilege is never shown twice; `status=superseded` or `status=all` shows the old ones. The status decisions of 3g refuse superseded SPKs and grants (422 `invalid_transition`, `appointment_not_current`).
- **Supervision links.** Supervised grants of other practitioners that name an old `full` grant are re-pointed to the new `full` grant of the same privilege (the supervisor of a grant is updatable for this use only), or get the open flag `supervisor_lost_privilege` when the new SPK has none. A carried supervised grant keeps its own supervisor and flag. A new supervised grant still needs the supervisor's active full grant (3g).
- No new log events: `application_create`, `application_update` and `application_decide` carry no SPK identifier, number or reason. No events are emitted and no alerts are sent.

## 3i. Shift definitions

- A shift belongs to one active facility of the tenant (422 `facility_not_found`, `facility_inactive`) and the facility, the code and the type never change. The code is 1 to 8 upper-case letters or digits, unique per facility and never reused, retired shifts included (409 `shift_exists`). The name is texts per language.
- The type is `regular`, `on_call_onsite`, `on_call_remote` or `off`. `off` has no times, no paid minutes and no night flag. The others need `startTime` and `endTime` as local `HH:mm`; an end earlier than the start means the next day, equal times are refused (422 `invalid_times`). Nothing is converted to an instant.
- Paid minutes run from 0 to the length of the shift (422 `paid_exceeds_duration`); a `regular` shift needs more than 0 (422 `paid_required`). How on-call time counts toward weekly hours is open (Q6): the working-time rules will read the number HR enters. `isNight` is entered by HR and does not follow the times.
- `unitIds` lists the units that may use the shift, empty meaning every unit of the facility. Each is an active unit of the shift's facility, without repeats, at most 100 (422 `unit_not_found`, `unit_closed`, `unit_outside_facility`, `duplicate_unit`, `invalid_units`). An edit rechecks the units only when `unitIds` is sent.
- `PATCH` changes `name`, times, `paidMinutes`, `isNight` and `unitIds`, needs at least one field (422 `empty_update`) and rechecks times and paid minutes together. A retired shift cannot be edited, retired again or reactivated (422 `shift_retired`); retiring is final and a shift that is needed again gets a new code.
- The list filters by `facilityId`, `status`, `type` and `unitId` (shifts that unit may use: the list is empty or holds it), ordered by facility then code. Reads write no log entry. Writes are logged as `shift_create`, `shift_update` and `shift_retire`, never a name, code or time. No events.
- Retiring a shift is refused while an active coverage requirement uses it, whatever its period, or while a planned assignment of it is in a roster that is not closed (409 `shift_in_use`, 3k and 3m).
- Not built: starter shifts per facility and sharing shifts across a facility group.

## 3j. Holiday calendars

- A calendar is one code in one year, unique per tenant (409 `calendar_exists`). The code is lower case, 2 to 32 letters, digits or hyphens starting with a letter; the year is 2000 to 2100; the country is an ISO 3166-1 alpha-2 code and the subdivision, when given, an ISO 3166-2 code of that country (format only). The code, year, country and subdivision never change. A calendar starts empty. Only tenant calendars are created, listed and changed; a platform calendar (no tenant) answers 404 like a foreign id.
- A holiday is a `YYYY-MM-DD` date inside the calendar's year, a kind (`public`, `collective_leave`, `local`) and a name per language. It is identified by date and kind (two kinds may share a date). A calendar holds at most 400 holidays, removed ones included (422 `too_many_holidays`).
- **Add by hand** makes a `manual`, `active` entry; an active day of the same date and kind answers 409 `holiday_exists`. Adding over a `removed` day brings it back as a `manual` entry with the new name. **Remove** sets the entry (imported or manual) to `removed` and deletes nothing; a day that is missing or already removed answers 404 `holiday_not_found`.
- The list filters by `code`, `year` and `country`, ordered by code then latest year, and hides removed holidays unless `includeRemoved=true`. Reads write no log entry.
- **CSV import.** `POST /v1/holiday-calendars/:id/imports` takes the file as a `text/csv` body of at most 512 KB (413 above it). The header is `date`, `kind` and one or more `name_<locale>` columns, nothing else (422 `invalid_header`); a file that is empty, not UTF-8, not a valid CSV, without rows or over `IMPORT_MAX_ROWS` rows answers 422 (`empty_file`, `invalid_encoding`, `invalid_csv`, `no_rows`, `too_many_rows`) and records nothing; a body that is not text answers 422 `csv_required`.
- A **check** (default) reads every row and records an `hr_imports` record, `validated` or `invalid`, with counts and at most `IMPORT_MAX_ERRORS` row errors. An error is a row number (the header is row 1), a column and a code (`invalid_date`, `date_outside_year`, `invalid_kind`, `missing_name`, `invalid_name`, `duplicate_row`), never a cell value. The calendar is not changed.
- **Apply** (`apply=true&checkId=<id>`, optional `version` and `reason`) needs the same file again: no file is stored, so the service hashes the body (SHA-256) and compares it to the check (422 `check_mismatch`; a missing, foreign, other calendar's, invalid or already applied check answers 422 `check_not_valid`, none 422 `check_required`). The same file cannot be applied twice to one calendar (409 `import_already_applied`); checking it again is allowed and reports everything skipped.
- **The merge** adds a new day and kind as `imported`; updates the names of an `imported` active day when they differ; and never touches a `manual` day or a removed imported day. A file never removes a day. It is recomputed against the calendar as it is at apply time, and the calendar, `last_import_id` and the import record change in one transaction. A stale calendar answers 409 `stale_version`.
- Writes are logged as `calendar_create`, `holiday_add`, `holiday_remove`, `holiday_import_check` and `holiday_import_apply`, with counts for the imports and never a date, a name, a cell or a reason. No events.
- `apps/utility/validation/csv.ts` (`readCsv`, on `csv-parse`) is the reader the roster import (3n) reuses.

## 3k. Coverage requirements

- A requirement is the minimum staffing of one unit for one shift. The unit and the shift never change. The unit must exist in the tenant and be `active` (422 `unit_not_found`, `unit_closed`); the shift must be `active` (422 `shift_not_found`, `shift_retired`), belong to the unit's facility (422 `shift_outside_facility`), be usable by the unit, its unit list being empty or holding it (422 `shift_unit_not_allowed`), and not be an `off` shift (422 `shift_not_countable`). A foreign, missing, malformed and deleted unit or shift give one answer.
- `dayPattern` is `all`, `weekdays` or `weekends_holidays` (422 `invalid_day_pattern`); which days these are is decided when rosters are checked (5.5). `minCount` is a whole number from 1 to 99 (422 `invalid_min_count`). `teamLeaderRequired` defaults to false.
- `match` has four optional criteria: workforce category, profession, specialty and minimum clinical level. Each is an active code of a `…workforce-category`, `…profession`, `…specialty` or `…clinical-level` system (422 `invalid_category`, `invalid_profession`, `invalid_specialty`, `invalid_clinical_level` for the wrong system; the concept service's `unknown_code` and `code_retired` for the code). An unset criterion matches anyone, so no criteria count every assigned employee.
- `period` has a real start date from 2000-01-01 and an end that is empty or not before the start (422 `invalid_period`). A start in the past is allowed.
- **No duplicates.** Two active requirements of the same unit, shift and day pattern with equal criteria and overlapping periods answer 409 `requirement_exists`; different criteria apply together. The check reads then writes, so two simultaneous requests can both pass.
- **Edit.** `PATCH` can change `dayPattern`, `match` (replacing all criteria), `minCount`, `teamLeaderRequired` and `period: { end }`, never the unit, the shift or the start. At least one field is needed (422 `empty_update`). **A requirement that has started** (its start is today or earlier in the unit's facility zone, UTC when that cannot be read) can change only `period.end`; anything else answers 422 `requirement_in_force`, so a changed rule is a new requirement that starts later and past roster checks do not change. A retired requirement cannot be edited (422 `requirement_retired`). Optional `version` (409 `stale_version`).
- **Retire** is final and stops the check for every date; a requirement that stops applying from a date is ended with `period.end`. Retired requirements stay in the list.
- The list filters by `unitId`, `shiftId`, `status`, `dayPattern` and `onDate` (period start on or before the date, end empty or on or after it), ordered by unit, shift and period start. Reads write no log entry. Writes are logged as `coverage_create`, `coverage_update` and `coverage_retire`, never a code, a count, a date or a reason. No events.
- Closing a unit is not blocked by its requirements; the roster checks ignore a closed unit (5.5).

## 3l. Rosters

- A roster is the plan of one unit for one period. The assignments, the validation and the coverage overrides are 3m. The unit, its facility, the period and the preparer never change. The unit must exist in the tenant and be `active` (422 `unit_not_found`, `unit_closed`); a foreign, missing, malformed and deleted unit give one answer. Any unit may have a roster.
- The **period** is checked against `ROSTER_PERIOD` read at the unit's facility (422 `invalid_period`): `month` is the first to the last day of one calendar month, `week` is Monday to Sunday and `two_weeks` a Monday to the Sunday after the next. A start in the past is allowed. Nothing is converted to an instant (`database.md` 4.4).
- A unit has at most one roster for a start date (409 `roster_exists`, backed by the unique index) and its rosters may not overlap (409 `roster_overlaps`, checked by reading then writing, so two simultaneous requests can both pass).
- **Status flow:** `draft`, `submitted`, `approved`, `published`, `closed`. `submitted` and `approved` can return to `draft`. Any other move answers 422 `invalid_transition`. Each step stamps who and when; `prepared_by` is the creator. A return clears the `submitted` and `approved` stamps and stores `return_reason`; the next submission clears it. Every move is written with the version it was read at, so two moves at once cannot both win (409 `stale_version`; an optional `version` in the body is checked first).
- **Approval is a setting.** `ROSTER_APPROVAL_REQUIRED` is read at the roster's unit at `submit` and `publish`. On: `submit` takes a draft to `submitted`, `approve` to `approved`, and `publish` needs `approved` (a draft answers 422 `approval_required`). Off: `publish` takes a draft directly and `submit` answers 422 `approval_not_required`. A roster already submitted or approved when the setting is turned off can still be approved and published; a submitted roster still needs `approve` first.
- **The gate.** `submit`, and `publish` of a draft when approval is not required, run the validation of 3m: a violation answers 422 `roster_invalid` and a gap that no override accepted 422 `coverage_gaps`; the summary is stored on the roster. Publishing an approved roster does not run it again.
- **Separation of duties.** The approver is never the preparer (403 `approver_is_preparer`); a roster prepared by a system actor is not blocked. A move without an acting account answers 403 `actor_required`.
- **Return** needs a reason of 1 to 500 characters (422 `reason_required`, `invalid_reason`) and works only from `submitted` or `approved`; a published roster changes assignment by assignment (3m).
- **Publish** sets `revision` to 1 (3m raises it on every change after publication). **Close** takes a `published` roster after its last day: the last day must be before today in the facility's zone (422 `period_not_ended`; UTC when the facility cannot be read). Attendance reconciliation is not built, so nothing is checked about it.
- The list filters by `unitId`, `facilityId`, `status` and a range `from` to `to` (a roster is in when its period overlaps it), latest period first. `GET /:id` answers 404 `roster_not_found` for a missing, malformed or foreign id. Reads write no log entry.
- Writes are logged as `roster_create`, `roster_submit`, `roster_approve`, `roster_return`, `roster_publish` and `roster_close`, never a date or a reason. No events and no notifications; `ROSTER_PUBLISH_LEAD_DAYS` is not enforced.
- Permissions: `workforce.roster:read`, `:write` (create, submit, publish, close) and `:approve` (approve, return), all tenant-wide until scoped permissions exist.

## 3m. Roster assignments

- An assignment puts one employee on one shift on one date in a roster. It stores the roster, unit, facility, employee, date, a **snapshot of the shift** (so editing the definition never rewrites the past), the shift's UTC `starts_at` and `ends_at` (null for an `off` shift), a role (`staff`, `team_leader`, `supervisor`, `dpjp_on_call`), a status (`planned`, `cancelled`), the source, the roster `revision` it carries, the overtime and a flag (never set yet). The roster, unit, facility, employee and date never change; move a person by cancelling and adding. Nothing is deleted.
- **Instants.** They are computed from the local date, the shift's `HH:mm` times and the facility's IANA zone with `zonedInstant` (`apps/utility/validation/local-date.ts`), DST-safe; an end earlier than the start ends the next day.
- **Add** (`POST /v1/rosters/:id/assignments`): the date is a real day inside the roster's period (422 `invalid_date`, `date_outside_period`); the shift is active, of the roster's facility and usable by the unit (422 `shift_not_found`, `shift_retired`, `shift_outside_facility`, `shift_unit_not_allowed`); the employee is an employee of the tenant on `probation` or `active` (422 `employee_not_found`, `employee_not_assignable`, `HR-ROS-001`); one planned assignment per employee, roster and date (409 `assignment_exists`); the unit is active (422 `unit_closed`); the role is valid (422 `invalid_role`). A clinical employee in a clinical unit must be **generally clinically eligible** on the date (conditions 1 to 4 of HR spec 5.5: status, a valid registration of the profession, a valid practice permit at the unit's facility, an active SPK that covers the unit; 422 `not_eligible_employment`, `not_eligible_str`, `not_eligible_sip`, `not_eligible_spk`, `HR-ROS-002`).
- **Working time** (`HR-ROS-010` to `013`, `015`, `016`), read from the employee's planned assignments of every roster and unit, with the limits of `MIN_REST_HOURS`, `MAX_WEEKLY_HOURS`, `MAX_OVERTIME_HOURS_WEEK` and `MAX_CONSECUTIVE_NIGHTS` at the roster's unit: no overlap (422 `overlap`), the minimum rest (422 `rest_too_short`), weekly paid minutes Monday to Sunday with overtime above `MAX_WEEKLY_HOURS` that needs the employee's consent (`overtimeConsent`, 422 `overtime_consent_required`) and stays under the weekly overtime limit (422 `overtime_limit_exceeded`), and the run of consecutive night shifts (422 `too_many_nights`). On-call shifts count at the paid minutes HR entered (Q6). The daily overtime limit is not checked. Add and change answer the first rule that is broken.
- **Change** (`PATCH /v1/roster-assignments/:id`) replaces the shift, the role or the overtime consent and rechecks the working time; at least one field (422 `empty_update`); a cancelled assignment cannot be changed (422 `assignment_cancelled`). **Cancel** (`POST .../cancel`) sets `status` to `cancelled`; a cancelled assignment counts in no check and frees the date. A missing, malformed or foreign assignment answers 404 `roster_assignment_not_found`; optional `version` (409 `stale_version`).
- **When a roster accepts changes.** A `draft` (a reason is optional and is not kept) and a `published` roster. A change to a published roster needs a reason of 1 to 500 characters (422 `reason_required`, `invalid_reason`), kept as `change_reason`, marks an added assignment with the source `change_request`, and raises `roster.revision` by one **in one transaction** with the assignment. A `submitted` or `approved` roster is frozen (422 `roster_locked`) and a `closed` one is final (422 `roster_closed`, `HR-ROS-040`).
- **The past** (`HR-ROS-041`): a date before today in the facility's zone is refused (422 `assignment_in_past`) unless the caller holds `workforce.roster:correct-past`; a correction always needs a reason. The handler learns the permission through `@CurrentPermissions()` (`authentication.md` 2).
- **List** (`GET /v1/rosters/:id/assignments`): filters `date`, `from`, `to`, `employeeId`, `status`, by date then employee, 1 to 500 per page. Reads write no log entry.
- **Validate** (`POST /v1/rosters/:id/validate`, `workforce.roster:validate`) runs every rule on the whole roster and answers `{ violations, coverageGaps, summary, checkedAt }`; it never refuses. Each assignment is checked against the employee's **earlier** assignments (date, start, id) in every roster, so a clash is reported once, on the later assignment. A violation names the rule, the employee, the date and the code, never a name. It also finds **seven days in a row without a rest day** (`HR-ROS-014`): a window of 7 days breaks the rule when the employee works every day of it (a day off, or a day with no shift, is a rest day), reported once per run. It stores only the counts on the roster (`validation`), so it raises the roster's `version`.
- **Coverage** (`HR-ROS-020`, `022`): for each day, shift and active requirement of the unit that applies that day (`weekdays` is Monday to Friday; `weekends_holidays` is Saturday, Sunday and the active holidays of the facility's holiday calendars), the planned assignments of the shift whose employee matches the criteria must reach `min_count` (the level means "this level or higher" by the rank of the code concept); a team leader requirement needs exactly one `team_leader` assignment whose employee meets the profession and the level. A gap names the day, the shift, the requirement, the reason (`min_count`, `team_leader`), what is required and what is there. A closed unit and retired requirements are not checked.
- **Overrides** (`POST /v1/rosters/:id/coverage-overrides`, `workforce.roster:override`) accept an existing gap with a required reason while the roster is a draft, submitted or approved (422 `override_not_allowed`, `no_such_gap`, `reason_required`; 409 `override_exists`). The gate (3l) lets an accepted gap through.
- **On duty** (`GET /v1/units/:id/on-duty?at=`, `workforce.roster-assignment:read`) answers the planned assignments whose shift contains the moment (start included, end excluded; now when `at` is missing) with their role, from published and closed rosters only, leaving out cancelled and flagged assignments. **My roster** (`GET /v1/employees/me/roster?from=&to=`) answers the signed-in employee's own planned assignments of published and closed rosters, ordered by date and start, for at most 62 days (422 `invalid_range`); it needs a linked employee (403 `employee_required`) and no permission. Neither writes a log entry.
- Writes are logged as `assignment_add`, `assignment_change`, `assignment_cancel`, `roster_validate` (with the counts) and `coverage_override`, never an employee, a date or a reason. No events and no notifications of a change.
- `workforce.roster-assignment:write` and the other permissions are tenant-wide until scoped permissions exist.

## 3n. Roster imports

- `POST /v1/rosters/:id/imports` takes a CSV as a `text/csv` body of at most 512 KB (413 above it; 415 for another type), like the holiday import. The header is `employee_number`, `date`, `shift_code` and optionally `role` and `overtime_consent` (`yes` or `no`), nothing else (422 `invalid_header`). The same reader errors apply (`csv_required`, `empty_file`, `invalid_encoding`, `invalid_csv`, `no_rows`, `too_many_rows` above `IMPORT_MAX_ROWS`). Only a `draft` roster takes an import (422 `roster_locked`, `roster_closed`); a closed unit answers 422 `unit_closed`.
- **Row checks** are those of the single add (3m), run from the same code (`assignment-checks.ts`): the employee is found by number in the tenant (`employee_not_found` for an unknown and a foreign number) and is on `probation` or `active`; the shift exists in the roster's facility and the unit may use it; the date is a real day inside the period and **not in the past**; the role is valid; a clinical employee in a clinical unit is generally eligible; the working-time rules hold. Cell problems are `invalid_employee_number`, `invalid_date`, `invalid_shift_code`, `invalid_role` and `invalid_consent`; a repeated employee and date in the file is `duplicate_row`. No reason or correct-past permission applies to an import. Each row stops at its first failing check.
- **Whole file.** Rows are checked in date, start and file order per employee, against the employee's planned assignments in every roster and the rows of the file accepted before, so a clash is reported once, on the later row. An existing planned assignment of the same roster and date is `assignment_exists`. Overtime needs `overtime_consent` on the row (`overtime_consent_required`). Seven days without a rest day and coverage are not row errors: the check answers their counts (`restDayGaps`, `coverageGaps`) next to the record, not stored.
- **Check** (default) records an `hr_imports` record of kind `roster_assignments`, target `{ roster_id }`, `validated` or `invalid`, with `rows`, `valid`, `invalid` and `created` counts and at most `IMPORT_MAX_ERRORS` row errors. A row error is a row number (the header is row 1), a column and a code, never a cell value. Nothing is written to the roster. The file is not stored: the record keeps its SHA-256.
- **Apply** (`apply=true&checkId=<id>`, optional `version` and `reason`) needs the same file again. Order of refusals: `check_required`; `check_not_valid` (missing, malformed, foreign, other roster's, cancelled, invalid or already applied check); `check_mismatch` (another file, by hash); 409 `import_already_applied` (the same file applied to this roster before); 409 `stale_version`. The file is then read and **checked again against the roster as it is now**. If any row fails, nothing is written, the import becomes `invalid` with the new errors and the answer is 422 `import_not_valid_anymore`. Otherwise one transaction writes every assignment through `createMany` and marks the import `applied` with counts and who; the answer is the import record.
- Each imported assignment has source `{ kind: 'import', ref_id: <import id> }`, the roster's `revision`, a snapshot of its shift, its UTC instants and the overtime and consent the row gave (consent has the apply time and no document). `createMany` records one change record per assignment with the reason `roster_import`; a `reason` in the query is kept on the import record. A second apply racing the first fails on the check's version and rolls back.
- `GET /v1/hr-imports/:id` views an import of any kind (roster or holiday): status, counts, row errors, who and when; no file content, no cell values. A missing, malformed or foreign id answers 404 `import_not_found`. `POST /v1/hr-imports/:id/cancel` takes a `validated` or `invalid` import to `cancelled` (422 `invalid_transition` otherwise; optional `version`, 409 `stale_version`); a cancelled check can no longer be applied, for either kind. Nothing is deleted.
- Writes are logged as `roster_import_check`, `roster_import_apply` and `hr_import_cancel`, with counts and the error class and `code` on failure, never a number, a date, a shift code or a reason. Reads write no log entry. No events and no notifications.
- Permissions are tenant-wide: `workforce.roster:import` for the roster route, `workforce.hr-import:read` and `:cancel`. A Head of Unit limited to their own unit comes with scoped permissions.

## 3o. Shift swaps

- A request asks to **trade** a shift (`counterpartAssignmentId` given) or to **hand it over** (not given) to a named colleague. It stores the unit, roster, the requester with their assignment, the counterpart (always named; `assignment_id` is `null` for a hand-over), the reason, the status, `counterpart_accepted_at`, the decision and `resulting_assignment_ids`. Only the status, `counterpart_accepted_at`, the decision and the resulting assignments change after creation. Nothing is deleted.
- **Who makes each move.** The signed-in employee asks (`POST /v1/shift-swaps`; the requester is the caller's linked employee, never a field), the named counterpart accepts (403 `not_the_counterpart`), the requester cancels (403 `not_the_requester`); these three and `GET /employees/me/shift-swaps` need a sign-in and a linked employee (403 `employee_required`) and no permission. `workforce.shift-swap:decide` approves and rejects, and is never exercised by the requester or the counterpart (403 `decider_is_party`); an account without a linked employee may decide. `workforce.shift-swap:read` lists the tenant's requests.
- **Status flow:** `requested` to `accepted_by_counterpart` (accept); `accepted_by_counterpart` to `approved` (approve); `requested` or `accepted_by_counterpart` to `rejected` (reject, reason required) or `cancelled` (cancel). Any other move answers 422 `invalid_transition`; `approved`, `rejected` and `cancelled` are final. Every move is written with the version it was read at (409 `stale_version`; an optional `version` in the body is checked first).
- **What can be swapped.** Both assignments are in one `published` roster (422 `roster_not_published`, `different_roster`) of an active unit (422 `unit_closed`), are `planned` (422 `assignment_not_planned`), not flagged (422 `assignment_flagged`) and dated today or later in the facility's zone (422 `assignment_in_past`), with no exception for any permission. The requester's assignment is their own (422 `assignment_not_yours`) and the counterpart's belongs to the counterpart (422 `counterpart_assignment_mismatch`). The counterpart is another employee of the tenant (422 `counterpart_not_found`, `counterpart_is_requester`). A missing, malformed or foreign assignment answers 404 `roster_assignment_not_found`, a request 404 `swap_not_found`.
- **One open request per assignment** (`requested` or `accepted_by_counterpart`), for either side (409 `swap_exists`). The check reads then writes, so two simultaneous requests can both pass; approve checks again.
- **The result.** In a trade the requester takes the counterpart's date, shift and role and the counterpart takes the requester's; in a hand-over the counterpart takes the requester's and the requester's assignment is cancelled. It is checked as if added by hand (3m, from `assignment-checks.ts`) with the replaced assignments taken out of each schedule: status `probation` or `active`, general clinical eligibility, one planned assignment per employee, roster and date (409 `assignment_exists`), overlap, rest, weekly hours and night runs (422 `overlap`, `rest_too_short`, `overtime_limit_exceeded`, `too_many_nights`, `not_eligible_*`, `employee_not_assignable`). **A result that would add overtime is refused** (422 `overtime_consent_required`): a swap has no place for the consent of 3m.
- **When it is checked:** at create, at accept and again at approve, always against the schedules as they are then. A failure at create or accept refuses the move; a failure at approve refuses the approval and leaves the request `accepted_by_counterpart` for the Head to reject.
- **Approve** (optional `version` and `reason` of 1 to 500 characters) writes in **one transaction**: the roster's `revision` plus one (written with the version it was read at), the original assignments `cancelled` (reason `shift_swap`, the new revision), the new assignments (source `{ kind: 'swap', ref_id: <request id> }`, the shift snapshot and UTC instants of the slot taken, the role, the new revision, reason `shift_swap`, no overtime) and the request `approved` with `decision` (`by` the acting account, `at`, `reason` or `null`) and `resulting_assignment_ids`. The assignments are created one by one (`createMany` is for imports). A stale roster or request answers 409 `stale_version`.
- **Reject** needs a reason of 1 to 500 characters (422 `reason_required`, `invalid_reason`), kept in `decision.reason`; a move without an acting account answers 403 `actor_required`. A counterpart who does not want the swap cannot decline: the requester cancels or the Head rejects.
- **Lists** (`GET /v1/shift-swaps`: `unitId`, `rosterId`, `status`, `employeeId` as requester or counterpart; `GET /v1/employees/me/shift-swaps`: `status`) take `limit` (1 to 100) and `offset`, latest first. Reads write no log entry. There is no single read.
- Writes are logged as `swap_create`, `swap_accept`, `swap_cancel`, `swap_approve` and `swap_reject` with the error class and `code` on failure, never an employee, a date, a shift or a reason (the reasons are `confidential` in the change log). No events and no notifications. The in-memory repositories cannot roll back, so tests check the results and a conflict raised before the write, not a failure in the middle of the approval.
- Permissions are tenant-wide: a Head of Unit limited to their own unit comes with scoped permissions.

## 3p. Practice schedules

- A practice schedule is the recurring weekly outpatient session of a doctor in a polyclinic: an ISO weekday (1 Monday to 7), a local start and end, an optional quota and a validity period, `active` or `ended`. The doctor, polyclinic, facility and weekday never change; a different doctor or day is a new schedule. Nothing is deleted. Dates and times are local to the facility (`database.md` 4.4).
- **Who can have one (`HR-ROS-004`).** The employee is a clinical Tenaga Medis (`id.workforce-category` with the code `tenaga_medis`) on `probation` or `active` (422 `employee_not_found`, `not_tenaga_medis`, `employee_not_assignable`) and **generally clinically eligible** for the polyclinic (conditions 1 to 4 of HR spec 5.5, `EligibilityService.general`) **on the first session date from today or the start of the validity, whichever is later** (422 `not_eligible_employment`, `not_eligible_str`, `not_eligible_sip`, `not_eligible_spk`; 422 `no_session_in_period` when the validity has no such weekday). The same check runs when an edit changes the times or the validity, and for the new date of a moved session. The polyclinic is an `active` unit marked clinical (422 `unit_not_found`, `unit_closed`, `unit_not_clinical`); unit types are tenant codes, so none is hard-coded.
- **Times, quota, validity.** `dayOfWeek` 1 to 7 (422 `invalid_day_of_week`). `startTime` and `endTime` are `HH:mm` and the end is **after** the start on the same day (422 `invalid_times`): a session does not run past midnight. `quota` is a whole number from 1 to 9999, or `null` for no limit (422 `invalid_quota`). `validFrom` is a real date from 2000-01-01 and `validUntil` is empty or not before it (422 `invalid_period`); a start in the past is allowed.
- **Edit** (`PATCH`) changes `startTime`, `endTime`, `quota` (`null` removes the limit), `validUntil` (`null` makes it open-ended) and `validFrom` **only before the schedule has started** (422 `schedule_started`). At least one field (422 `empty_update`); an `ended` schedule cannot be edited (422 `schedule_ended`); optional `version` (409 `stale_version`).
- **No double booking.** A doctor cannot have two sessions that overlap in time on the same weekday in periods that share a day, **in any polyclinic** (409 `schedule_overlaps`); sessions that only touch do not overlap, and an ended schedule counts until its last date. The check reads then writes, so two simultaneous requests can both pass. A clash with the doctor's roster assignments is not checked.
- **End** (`POST .../end`, `lastDate`) sets `period.end` to the last day the schedule applies and `status` to `ended` **at once**: `ended` means closed to edits, not "no longer applies", so the sessions up to `lastDate` are still offered. `lastDate` is today or later, not before the start and not after the current end (422 `invalid_last_date`); a second end answers 422 `schedule_ended`.
- **Sessions of a date** (`GET /v1/practice-schedules?date=`, optional `unitId`, `employeeId`, `limit`, `offset`) answer one session for each schedule whose weekday is the date's and whose period covers it, whatever its status, plus sessions moved onto the date. A session has `scheduleId`, `employeeId`, `displayName` and `specialties` of the doctor (public inside the hospital), `unitId`, `facilityId`, `date`, `startTime`, `endTime`, `quota`, a `state` (`scheduled`; `cancelled`; `moved` with `movedTo`; `moved_in` at its new time) and `eligible` with `failed`, **derived from the records at the time of the call and never stored** (`HR-ELG-001`). A doctor or unit that cannot be read is `eligible: false`. Ordered by polyclinic, start time and doctor; the regular and the moved-in lists are merged and then paged. Any date is answered, a past one too. Without `date` the route lists schedules (`unitId`, `employeeId`, `status`), ordered by polyclinic, weekday and start time.
- **Exceptions** (`POST .../:id/exceptions`): `date` must be a session of the schedule, its weekday inside its period (an ended schedule serves its days; 422 `no_session_on_date`), and today or later (422 `date_in_past`); `kind` is `cancelled` or `moved` (422 `invalid_kind`); `reason` is an active code of `id.practice-exception-reason` (422 `invalid_exception_reason`, and the concept errors `unknown_code`, `code_retired`, `code_not_in_period`); `movedTo` is required for `moved` and refused for `cancelled` (422 `moved_to_required`, `moved_to_not_allowed`) with a real date today or later, valid times and not the time the session already has (422 `invalid_date`, `date_in_past`, `invalid_times`, `not_moved`). One exception per schedule and date (409 `exception_exists`); optional `version` is the schedule's (409 `stale_version`). The doctor and the polyclinic are copied from the schedule and the source is `manual`.
- **A moved session follows the rules of a schedule:** the doctor is generally eligible on the new date and is not in two places, against their regular sessions that are not cancelled or moved away and the sessions moved onto the date (409 `schedule_overlaps`). A session may move inside its own date, and onto a time freed by a cancelled session.
- **Undo** (`POST /v1/practice-schedule-exceptions/:id/cancel`, optional `version` and `reason`) **soft-deletes** the exception (`deleted_at`), so the session is back and the change history keeps who undid it. The unique index per schedule and date ignores soft-deleted records, so a new exception can follow. It needs a date today or later (422 `date_in_past`), refuses to bring a session back onto a time the doctor now uses (409 `schedule_overlaps`) and answers the exception as it was. A missing, malformed, foreign or already undone exception answers 404 `exception_not_found`; a schedule 404 `schedule_not_found`.
- Writes are logged as `practice_schedule_create`, `practice_schedule_update`, `practice_schedule_end`, `practice_exception_create` and `practice_exception_cancel` with the error class and `code` on failure, never a doctor, a date, a time, a code or a reason. Reads write no log entry. Schedules are `public` and exceptions `internal` in the change log. No events and no notifications.
- Permissions are tenant-wide: `workforce.practice-schedule:read` (registration's service account holds it) and `:write`. A Head of the polyclinic limited to their own unit comes with scoped permissions.

## 4a. Events

Workforce writes events to the event outbox in the same transaction as the data (`database.md` 7.1). Plan: `.claude/design/plans/gateway-hr-events-to-identity.md`.

| Event | Emitted by | Payload |
|---|---|---|
| `workforce.employee.status_changed` | `EmployeeService.changeStatus` | `employee_id`, `from_status`, `to_status`, `effective_date` |
| `workforce.contract.activated`, `.ended`, `.terminated` | `ContractService` | `contract_id`, `employee_id`, `organization_id` |

- A refused change (invalid transition, stale version, failed activation) writes no event. Registering an employee emits nothing.
- Payloads hold identifiers, codes and dates only, never a name, number, contact, reason or note.
- Identity reacts to status changes with account holds (`authentication.md` 5). Contract events are published and ignored for now. Delivery is at least once, in order, by the worker's relay (`logging.md` 14); the worker must be running for holds to be applied.
- A new HR event adds its name and payload to `workforce-event.ts`, an emit inside the writing transaction, and a test that it is written once, with the right correlation id and no personal values.

4. Add the service in `workforce/<area>/` with its spec (in-memory repositories): happy paths, every rejection, tenant isolation, stale version, reads write no log, writes log no values.
5. Add the permissions to the catalog.
6. Add the controller, DTOs and module in `gateway_hr/src/<area>/`, import the module in `GatewayHrModule`, and write the gateway test with `createHrGateway` (`facility.spec.ts` is the reference): 401, 403, happy paths, 404 for malformed, missing and foreign ids, 409 cases, validation, list limits, reads write only the access log, writes log no values.
7. Update `workforce.md` (permissions, rules), the status in `hr-endpoints.md` and the plan, in a **separate documentation PR** after the code merged. ## 6. Running

| Command (from `apps/back-end`) | Does |
|---|---|
| `pnpm start:dev:hr` | Runs `gateway_hr` with reload on port 3001 (`NODE_PORT`). |
| `pnpm start:hr`, `pnpm start:prod:hr` | Run it once, from source or from `dist`. |
| `pnpm build:hr` | Builds only `gateway_hr` (`pnpm build` builds all applications). |
| `pnpm type-check` | Checks `gateway_back_office`, `gateway_hr` and `worker`. |

From the repository root, `pnpm dev:hr` starts it. The application needs the same environment files as `gateway_back_office` (`application`, `mongo`, `logger`, `change-log`, `auth`) and a MongoDB replica set.

`gateway_hr` also needs `encryption.env` (`ENCRYPTION_MASTER_KEY`, `ENCRYPTION_HASH_KEY`: base64, 32 bytes each, `openssl rand -base64 32`). Never commit it; back both keys up, because losing the master key makes stored profiles unreadable and changing the hash key breaks identifier uniqueness checks.

No first administrator exists (`authentication.md` 5). To call HR endpoints by hand, insert an account, a role holding the HR permissions and a tenant binding with `mongosh`, then sign in on `gateway_back_office`.
